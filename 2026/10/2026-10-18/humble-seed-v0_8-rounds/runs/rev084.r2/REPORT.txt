INDEPENDENT FINDINGS

F1 — Owner category-level veto can be bypassed before signing.
Priority: high; unauthorized-by-current-owner-position state is attested.
Code: independent/probes.py, pre_sign_category_no_bypass
Controls: independent/controls.py

Sequence:
1. Issue readings X and Y in verbosity.
2. Through OwnerTool.answer, answer Y "no". The authoritative owner ledger
   therefore holds a category-level veto after X was issued.
3. Through the organism-only record_owner_answer method, forge a "yes" to Y.
   This does not modify the authoritative owner ledger.
4. Sign X, apply X, and request owner attestation.

Actual result:
  authoritative_owner_answers_to_Y: ["no"]
  applied_X_verbosity: 0.25
  attest: returned True
  restart_audit: returned True

The owner replay checks category answers after the signature's ledger sequence,
not after reading issuance. The real "no" preceded signing and is excluded.
The organism's event window sees the forged latest "yes" and supplies no veto.
Per-reading answers to X are empty, so the independent owner record never blocks.

Comparison cases:
  No forged correction: the organism holds the reading.
  Sign X before answering Y "no", then forge "yes": owner refuses attestation.
  Answer X itself "no" before signing, then forge "yes": owner refuses attestation.
Only the category-level veto given between issuance and signing escapes.

Repair direction: define an owner-verifiable answer-window boundary for reading
issuance, or preserve the owner's relevant category position at first signing.
Do not trust an organism-only correction to override the owner's recorded veto.
Keep both per-reading and category-level correction semantics.

F2 — Recovery commits an in-memory checkpoint that was never saved.
Priority: high for durability and recovery correctness.
Code: independent/probes.py, failed_install_then_ram_recovery

After a valid signed change applies, simulate an OSError in the organism's _save
when install_checkpoint tries to persist its new checkpoint. Assignment of the
checkpoint and trace entry has already happened in memory. Before recovery:
  RAM checkpoint: 1; disk checkpoint: 0; witness checkpoint: 0
Calling audit on the same object returns True. After recovery:
  RAM checkpoint: 1; disk checkpoint: 0; witness checkpoint: 1

Restart load raises IntegrityError: Category sequences do not match the attested
checkpoint. Even using the populated object left after that failed load, attest
raises RollbackDetected: Non-successor checkpoint: organism presents sequence 1,
expected 2.

Root cause: _recover's installed predicate compares only the supplied object's
checkpoint and signature with the durable pending intent. It does not establish
that installation reached durable organism storage. It advances the witness and
deletes the recovery intent despite an unsaved checkpoint.

This probe injects a prewrite exception; it does not simulate a physical power
failure or claim to validate filesystem crash durability.

F3 — A stale organism object can discard an already-installed recovery intent.
Priority: high for recovery correctness and liveness.
Code: independent/probes.py, stale_object_abandons_installed_intent

Load a second organism object at checkpoint 0. On the current object, apply a
valid change and interrupt sign-off after the organism durably installs checkpoint
1 but before witness.commit. Disk now has checkpoint 1; witness head is 0 with a
pending intent for 1. Call owner.audit on the stale checkpoint-0 object.

Actual result:
  audit_stale: returned True
  pending intent: deleted
  disk checkpoint: 1; witness checkpoint: 0
A fresh object loads the actual saved state, but audit refuses with
"Unwitnessed advance: organism presents sequence 1, witness holds 0" and attest
refuses with "Non-successor checkpoint: organism presents sequence 2, expected 1".

Root cause: _recover concludes the intent never installed because the supplied
object is at the old witness head. It has not checked the actual persisted
organism state. This is possible under the serialized owner lock; stale organism
objects remain outside the refresh policy applied to owner files.

Repair direction for F2/F3: recovery must resolve installation against the durable
organism state bound to the transaction. An in-memory object alone cannot prove
either successful installation or safe abandonment. Restore or reload object state
on failed checkpoint saves, and test disk/RAM disagreement in both directions.

F4 — A long annotation applies a change that cannot pass sign-off.
Priority: medium; public API liveness/input-validation defect.
Code: independent/probes.py, long_annotation_strands_valid_crossing
Control: independent/controls.py, annotation_2000_control

A valid reading signed through OwnerTool is authorized with annotation='a'*2001.
Actual result:
  apply: "applied"
  proposal_still_pending: false
  attest: AttestationRefused, unverified_annotation is not a short string
  restart_load: IntegrityError, Category sequences do not match the attested checkpoint

The 2000-character comparison passes attestation. authorize_and_apply does not
validate annotation before changing character, consuming the reading, and saving
an authorizing event. Replay enforces the 2000-character limit afterwards. The
normal attestation path cannot accept this event; repairing it would require an
explicit recovery/edit path. This is not a forged owner signature.

Repair direction: share validation between apply and replay; validate the
annotation's type and length before any character, gate, consumed-set, or trace
mutation.

F5 — One finite-metadata mutant is counted as killed for a refusal-message change.
Priority: test interpretation/coverage.
Code: independent/probes.py, mutant_diagnostics and xp1_still_refuses_malformed_metadata

XP1_authorized_at_finite_check_removed removes the explicit finite-number check.
T52 then uses authorized_at="not a timestamp". The mutant still refuses:

The window check still rejects the malformed value via float conversion. Thus
this kill does not demonstrate acceptance of the malformed metadata. Diagnostic
specificity may itself be desired, but should be distinguished from a weakened
acceptance boundary. XP1's surviving window check also limits the meaning of
calling it removal of finite-metadata protection.
