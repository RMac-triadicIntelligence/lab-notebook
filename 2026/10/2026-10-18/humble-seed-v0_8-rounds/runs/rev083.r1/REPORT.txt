EXECUTIVE ASSESSMENT

The shipped run reproduces exactly, down to the complete results.json bytes.
47/48 test expectations and 40/41 mutant expectations match the frozen declaration.
The two mismatches share one cause: T26 catches the intended unsigned-change
attack earlier than predicted. Its defensive behavior works. Correcting a real
answer from no to yes also works through attestation, reload, and audit.

The new owner ledger is useful, but it is not yet a reliable shared authority.
A second open owner session can leave the first acting on stale records. That
allows a real owner's no to be bypassed, a valid signature record to be erased,
and the first-signing lifetime to be refreshed. The witness has the same cached
state problem: two open sessions can attest competing sequence-1 checkpoints
from the same parent. None of these probes edits the owner files or steals a key.

Replay also accepts forged timestamp and note values. This does not falsify the
character destination or rendered consequence, but it disproves the literal
claim that every record field is checked. Three new metadata mutants survive
all 47 tests that pass on the baseline, without newly failing or crashing a test.

An injected witness-write failure exposes an additional recovery problem: the
organism advances durably while the witness stays behind, and ordinary audit
and attestation retry both refuse after reopening.

Recommendation: keep candidate status. Prioritize one serialized, durable owner
state authority covering signatures, answers, witness heads, and checkpoint
commit/recovery. These failures concern the implementation of the authority,
not evidence against the broader external-authorization idea.

FINDINGS

F1 — HIGH, CONDITIONAL ON MULTIPLE OPEN OWNER INSTANCES
Stale OwnerLedger snapshots bypass or destroy authoritative owner records.

Affected: OwnerLedger.__init__, _persist, signed, answers_to,
answers_in_category_after; OwnerTool.sign_proposal and _check_owner_acts.
The ledger is read at construction, thereafter queried from memory, and each
write replaces the whole file. There is no lock, reload, version check, or
single-writer enforcement. Sequential calls from overlapping instances suffice;
simultaneous threads or a precise race are unnecessary.

Reproducer: code/independent_probes.py, stale_owner_veto_bypass.
1. Session A signs a reading. Session B opens the same owner ledger and witness.
2. B records the owner's real no. It is present in the durable owner file.
3. The untrusted organism records a forged yes, as in the shipped T47 threat.
4. The organism applies the reading. A attests using its stale answer snapshot.
5. A fresh owner sees the durable no, yet reload+audit accepts the checkpoint.
Observed: durable_owner_answers=['no']; attestation_accepted=True;
fresh_reload_and_audit=True; verbosity=0.25; witness_sequence=1.
Fresh-session control: the up-to-date session refuses this same forged-yes
scenario for the owner's position. The bypass is caused by stale owner state.
No owner file is directly edited by the probe. The signature is valid.

Two further reproducers isolate consequences of the same root cause:
- stale_owner_erases_signature: B opens before A signs. B later records an
  ordinary yes and replaces the file with its old signed-record map. A fresh
  owner loses the valid signature record and refuses the legitimate crossing
  as “not signed through this owner tool.” This needs no forged evidence.
- stale_signer_refreshes_lifetime: B opens before A's first signature. A signs
  at t0; B signs the exact same payload at t0+11 with TTL 10. The durable first
  signing time shifts by 11 seconds and attestation succeeds. Owner clocks
  are explicitly injected for the test; the organism remains within its own
  issuance-time window. One-instance control correctly refuses after 11 seconds.

Why fresh audit does not repair the bypass: audit validates the existing signed
checkpoint and witness head. It does not redo the owner acts that were checked
before that checkpoint. Reloading the ledger after an incorrect attestation is
therefore too late to withdraw that checkpoint through the ordinary audit path.

Repair direction: serialize all owner operations against one current durable
record. A lock must cover read, checks, update, and commit, or use a transactional
store with versioned conditional updates. Preserve first-signing events.
Simply reloading in one getter leaves races between checks and writes. If the
intended deployment permits only one owner process, enforce that exclusivity
and make a second instance refuse before it can perform owner operations.

F2 — HIGH, CONDITIONAL ON MULTIPLE OPEN WITNESS INSTANCES
Two valid sibling checkpoint attestations are issued from one witness parent.

Affected: OwnerWitness.__init__, check_successor, record, _persist;
OwnerTool.attest. Like the ledger, the witness only reads its file at creation.

Reproducer: stale_witness_fork.
Start with one enrolled sequence-0 organism and two legitimately signed readings,
one for verbosity, one for formality. Load the same organism state into two
objects and open two owner sessions against the same files. Session A applies
and attests the verbosity branch. Session B then applies and attests the
formality branch using its stale sequence-0 witness snapshot.
Observed: both checkpoints have sequence 1 and the same parent, but different
checkpoint hashes and different character. Both attest calls return True.
Both existing sessions audit their own branch as current. A freshly opened
session accepts branch B and detects branch A as a fork.

This does not show that a fresh witness accepts both histories. It shows that
the provided witness implementation issued and locally accepted two competing
histories before a fresh witness noticed. No direct file tampering, clock
changes, source patches, or deliberately faulty cryptography are involved.
The on-disk organism state ends on the second branch; both checkpoint objects
and signatures have nevertheless been issued and remain independently valid.

Repair direction: share the serialization mechanism from F1. Enforce successor
selection atomically at the authoritative durable head. Avoid releasing a new
valid checkpoint based on a stale head; define how commit and install recover
from interruption. A write-time refresh alone, after signing/installing a
checkpoint, is too late to prevent issuance of competing signatures.

F3 — MEDIUM, RECORD INTEGRITY; NO CHARACTER-DESTINATION BYPASS
“Every record field” is stronger than the implementation and tests establish.

Affected: replay_signed_history (especially the record checks near lines
1373–1385); T44_replay_checks_every_record_field.

Reproducer: forged_record_metadata.
After a legitimate signed apply, before attestation, edit only the untrusted
organism's unattested tail, recompute its unsigned hash chain and state digest:
- record.authorized_at = 'not a timestamp'
- record.note = {'forged': 'owner said yes; real owner note was empty'}
- authorized_mutation.timestamp = -123456789.0
The owner attests. Fresh reload and audit accept all these values.
No previously attested prefix or owner-side records are changed.

The code verifies the record field-name set and many values used in replay,
but never validates authorized_at or note, nor binds the outer event timestamp
to the record time. Python dataclass annotations do not enforce types on load.
T44 exercises only prior_value, first_commit, and prior_character_snapshot.

Three separate supplemental mutants establish the test coverage gap:
XM1_invalid_authorized_at: every new record gets authorized_at='not a timestamp'.
XM2_forged_owner_note: every new record replaces owner_note with a forged dict.
XM3_inconsistent_event_timestamp: mutation event time becomes -123456789.0.
All three SURVIVE: no new FAIL or ERROR among the 47 passing baseline tests.
These results are supplemental, not additions to the frozen 41-mutant score.
Exact source edits, full mutant sources, and all 48 outcomes per mutant are saved.

Limit: the forged metadata does not reverse the rendered consequence. Character,
prior value, distribution, derived destination, and other checked replay fields
still agree in this probe. Treat this as an audit-record/type/authenticity gap,
not a demonstrated defeat of destination derivation or lifetime checks. Lifetime
uses owner ledger signed_at and the owner clock, not this forged authorized_at.

Repair direction: define field provenance explicitly. Validate finite numeric
record/event times and structural agreement. Do not claim that an owner note is
authenticated unless the owner stores or signs that exact note. If organism
notes are allowed, label them as untrusted organism annotations. Tests should
cover every supported field's type and source of authority.

F4 — MEDIUM, AVAILABILITY / RECOVERY
A witness persistence failure strands the normal attestation workflow.

Affected: OwnerTool.attest installs the organism checkpoint before
OwnerWitness.record persists the witness advance.

Reproducer: witness_write_failure.
Inject OSError into witness._persist only for the second attestation, after a
legitimate signed crossing. The organism durably stores checkpoint 1. Witness
persistence fails; the on-disk witness remains 0. Reopen both sides.
Observed: organism.load succeeds; fresh audit refuses “Unwitnessed advance:
organism presents sequence 1, witness holds 0.” Retrying OwnerTool.attest
refuses “Non-successor checkpoint: organism presents sequence 2, expected 1.”
This is an explicit fault injection, not an observed spontaneous disk failure.

Limit: fail-closed behavior protects against an unwitnessed advance. This probe
shows a missing normal retry/recovery path, not an unauthorized accepted change.
It is not the already listed lost-ledger or expired-attestation limitation: the
ledger is present, the TTL is current, and the failure is between durable writes.
Manual or lower-level recovery may be possible; it is not provided by the two
normal calls tested here.

Repair direction: a documented, recoverable checkpoint commit protocol tying
organism install and witness advancement to one durable intent/transaction.
Test restart at each durable boundary and verify idempotent completion or
explicit recovery. Do not blindly reverse write order, which creates a different
half-committed state.
